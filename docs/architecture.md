## 1. Что делает система

Проект реализует **визуально управляемое сопровождение цели дроном в симуляции**: беспилотник
обнаруживает человека камерой, выбирает конкретную цель, удерживает её в кадре и физически летит
следом, сохраняя заданную дистанцию, — и при этом ведёт себя безопасно (границы полёта, возврат
домой по исчерпании ресурса). Ключевая формула — замкнутый контур **«восприятие → решение →
управление»**:

```
Камера → Детектор → Трекинг/идентичность → Решение (регулятор) → Движение → (новый кадр)
```

Всё работает в программной симуляции (Software-In-The-Loop): реальный код автопилота и реальный
конвейр компьютерного зрения исполняются на одной машине, физика и изображение синтезируются
симулятором. Реального летательного аппарата в контуре нет.

## 2. Технологический стек и стандарты

| Слой | Технология | Стандарт / роль |
|---|---|---|
| Симуляция физики и сенсоров | **Gazebo Harmonic** (`gz-sim`) | Синтез динамики аппарата, рендеринг изображения камеры |
| Автопилот | **PX4 SITL v1.15.4** | Промышленный автопилот, исполняемый как программа; внутренняя шина сообщений — **uORB** |
| Middleware приложения | **ROS2 Humble** | Модель «узлы + топики» поверх **DDS** (Data Distribution Service, стандарт OMG); транспорт — RTPS |
| Мост «автопилот ↔ ROS2» | **Micro-XRCE-DDS-Agent** + `px4_msgs` | Стандарт **XRCE-DDS** (DDS для устройств с ограниченными ресурсами): пробрасывает uORB-топики PX4 в ROS2 как топики `/fmu/*` |
| Мост камеры | **`ros_gz_bridge`** | Перекладывает изображение из Gazebo в ROS2-топик `sensor_msgs/Image` |
| Детекция объектов | **YOLO (Ultralytics), модель YOLOv8n** | Свёрточный детектор; классы — **COCO** (используется `person`) |
| Мультитрекинг | **ByteTrack** (встроен в Ultralytics) | Ассоциация детекций между кадрами → устойчивый `track_id` |
| Ре-идентификация | **OpenCLIP ViT-B-32** | Извлечение эмбеддинга облика; сравнение по косинусной близости |

### 2.1 Как строки таблицы связаны друг с другом

Строки таблицы уже расположены в порядке «снизу вверх» — от физики к прикладной логике; ниже они
разбираются в том же порядке (сверху вниз по тексту таблицы = снизу вверх по стеку абстракции).
Каждый слой оборачивает предыдущий и передаёт данные наверх через стандартизированный мост, а не
напрямую:

1. **Gazebo Harmonic** синтезирует физику и рендерит камеру. У неё нет понятия ROS2 или PX4 — она
   отдаёт состояние мира и картинку по своему внутреннему протоколу (`gz-transport`).
2. **PX4 SITL** получает от Gazebo синтезированные сенсоры, исполняет логику автопилота и
   отдаёт команды на моторы обратно в Gazebo — напрямую, без ROS2 между ними. Внутри себя PX4
   общается через **uORB**, отдельную от ROS2 шину. Эта пара (Gazebo ↔ PX4) работает в
   **lockstep** (см. §3) и не знает о существовании следующих слоёв.
3. **ROS2 Humble** — самостоятельный прикладной слой, отдельный от связки Gazebo/PX4. Сам по
   себе он не имеет доступа ни к uORB, ни к рендеру Gazebo — ему нужен мост к каждому из них.
4. **Micro-XRCE-DDS-Agent** + `px4_msgs` — мост, который берёт uORB-топики PX4 (шаг 2) и
   представляет их в ROS2 (шаг 3) как топики `/fmu/out/*` (телеметрия наружу) и `/fmu/in/*`
   (команды внутрь). `px4_msgs` даёт типы сообщений, идентичные uORB-структурам, чтобы ROS2-узел
   мог их десериализовать. Без этого моста PX4 и ROS2 — два изолированных мира.
5. **`ros_gz_bridge`** — второй, независимый мост: не трогает PX4/uORB, а просто перекладывает
   картинку из Gazebo (шаг 1) в ROS2-топик `sensor_msgs/Image`. Существует отдельно от XRCE-моста,
   потому что решает другую задачу (видео, а не телеметрия/команды).
6. **YOLOv8n** — логика внутри ROS2-узла (`detector_node`), не мост. Берёт кадр, полученный через
   `ros_gz_bridge` (шаг 5), и находит на нём объекты классов COCO (используется `person`). Выход —
   bbox + класс + уверенность на каждый кадр отдельно, без памяти о предыдущих кадрах.
7. **ByteTrack** работает поверх YOLO, встроен в тот же вызов Ultralytics (`model.track()`).
   Связывает детекции YOLO (шаг 6) между кадрами, выдавая устойчивый `track_id` — то есть
   добавляет «память» во времени, которой нет у самого YOLO.
8. **OpenCLIP ViT-B-32** — отдельная, более тяжёлая сеть, включается только когда ByteTrack
   (шаг 7) теряет трек. Превращает вырезанную фигуру в эмбеддинг и сравнивает его косинусной
   близостью с сохранённым эталоном облика цели. Резервный уровень поверх ByteTrack, а не замена
   ему: считается не каждый кадр, а только по необходимости — экономия GPU.

Итого: Gazebo и PX4 работают в связке напрямую, к ней пристыкованы два независимых моста в ROS2
(XRCE — для автопилота, `ros_gz_bridge` — для камеры), а внутри ROS2-узла зрения три CV-технологии
образуют каскад с понижением частоты обращения: YOLO — каждый кадр → ByteTrack — тоже каждый кадр,
но с памятью → OpenCLIP — только при потере трека.

**Почему ROS2, а не прямое управление через MAVLink/MAVSDK.** ROS2 — индустриальный способ
строить робототехнические системы: узлы обмениваются типизированными сообщениями через
именованные топики, а не вызывают друг друга напрямую. PX4 подключается к этой модели нативно
через мост XRCE-DDS, поэтому отдельный протокол MAVLink для базового контура не нужен
(обоснование — `project_plan.md` §3, Р1/Р6).

## 3. Ключевые доменные понятия

Поясняются термины, без которых поток данных ниже не читается.

- **SITL (Software-In-The-Loop).** Автопилот PX4 исполняется как обычный процесс, без бортового
  контроллера. Он «думает», что летит: получает синтезированные сенсоры от Gazebo, выдаёт команды
  на двигатели обратно в Gazebo.
- **uORB** — внутренняя публикация/подписка внутри PX4. Наружу (в ROS2) эти сообщения выходят
  через мост XRCE-DDS под именами `/fmu/out/*` (телеметрия из автопилота) и `/fmu/in/*`
  (команды в автопилот).
- **Lockstep** — режим, в котором симулятор и автопилот шагают синхронно (симуляция ждёт
  автопилот и наоборот). Даёт детерминизм, но чувствителен к нехватке ресурсов: если рендеринг
  или инференс не успевают, шаг «залипает» и PX4 теряет данные сенсоров.
- **Offboard-режим** — режим PX4, в котором управление аппаратом задаётся **внешними уставками**
  (setpoint) от нашего кода, а не встроенной миссией. Критическое требование: поток уставок
  должен идти **непрерывно, с частотой выше 2 Гц**, иначе автопилот выходит из offboard. Поэтому
  контроллер — это постоянный цикл, публикующий уставку **каждый тик** (даже «висеть» — это
  уставка с нулевой скоростью), а не разовая команда. Порядок входа строгий: сначала поток
  уставок, затем переключение в offboard, затем арминг (снятие с предохранителя).
- **Системы координат.** «Тело» аппарата (**body frame**: вперёд/вправо относительно носа) и
  навигационная **NED** (North-East-Down: ось Z направлена **вниз**, поэтому высота — это `−z`).
  Регулятор считает команду «вперёд» в body-frame, затем поворачивает её в NED по текущему курсу
  (heading). Уставки в PX4 задаются в NED.
- **Setpoint (уставка)** — целевое значение, которое отрабатывает автопилот. Здесь используются
  уставки **скорости** (vx, vy, vz в NED и угловая скорость по рысканью — yaw rate).
- **`track_id` против `object_id`.** `track_id` — **временный** номер трека от ByteTrack: он
  умирает вместе с треком при перекрытии/выходе из кадра и возвращается уже другим числом.
  `object_id` — **постоянный** идентификатор сопровождаемого человека, присваиваемый по «облику»
  (эмбеддингу) и переживающий смену трека. Различие — ядро сопровождения именно *конкретной*
  цели.
- **Эмбеддинг и косинусная близость (ReID).** Изображение вырезанной фигуры человека
  преобразуется нейросетью в вектор признаков (эмбеддинг). «Похожесть» двух фигур измеряется
  косинусом угла между их векторами; порог косинуса решает, тот же это человек или другой.
- **Pinhole-модель дистанции.** По геометрии камеры-обскуры: дистанция `d ≈ f_y · H / h_px`, где
  `H` — известный рост цели (м), `h_px` — высота её bbox в пикселях, `f_y` — фокусное расстояние
  камеры. Даёт метрическую оценку дистанции из одного кадра.
- **P/PID-регулятор.** Пропорциональный член реагирует на текущую ошибку (`kp·e`), интегральный —
  накапливает ошибку и убирает установившееся смещение, дифференциальный — гасит колебания.
- **FSM (конечный автомат)** — набор явных состояний поведения контроллера (взлёт, слежение,
  потеря, поиск, возврат) с определёнными переходами.
- **Geofence / RTL.** Geofence — виртуальная граница зоны полёта. RTL (Return-To-Launch) —
  штатный режим PX4 «вернуться к точке старта и сесть».

## 4. Структура: colcon-workspace и модули

Проект — **не плоский Python-репозиторий, а colcon-workspace ROS2**: код разложен по
**ament-пакетам** в `src/`, собирается `colcon build` и запускается через `ros2 launch`. Каждый
пакет — отдельная зона ответственности; узлы общаются **только через топики**, не импортируя друг
друга.

```
src/
├── drone_interfaces   # определения сообщений (контракт между узлами)
├── drone_simulator    # запуск симулятора: мир, модель дрона/камеры, мосты
├── drone_perception   # detector_node — зрение (детекция, трекинг, ре-идентификация, дистанция)
├── drone_control      # follower_node — управление (регуляторы, FSM, безопасность, offboard-цикл)
└── drone_bringup      # launch-файлы, связывающие узлы в пайплайн
```

### 4.1 `drone_interfaces` — контракт данных

Содержит единственное кастомное сообщение **`Target.msg`** — то, что детектор сообщает
контроллеру о цели. Координаты **нормализованы** (`[-1..1]` от центра кадра, доля площади),
поэтому коэффициенты регулятора не зависят от разрешения камеры.

| Поле | Тип | Смысл |
|---|---|---|
| `header` | `std_msgs/Header` | Временная метка кадра — контроллер по ней оценивает свежесть цели |
| `detected` | `bool` | Есть ли цель в кадре сейчас |
| `offset_x` | `float32` | Смещение центра bbox от центра кадра по X (право > 0) → канал рыскания |
| `offset_y` | `float32` | Смещение по Y (вниз > 0) → guard кадрирования |
| `area_ratio` | `float32` | Доля площади кадра под bbox — прокси дистанции (fallback) |
| `track_id` | `int32` | Временный id трека (ByteTrack); `−1` — нет |
| `distance_m` | `float32` | Честная дистанция в метрах (pinhole); `0` — нет оценки |
| `object_id` | `int32` | Постоянный id сопровождаемого человека; `−1` — цель не захвачена |

Новые поля Фазы 4 добавлены **в конец** сообщения — это ABI-совместимо, старые потребители не
ломаются.

### 4.2 `drone_simulator` — симулятор и мосты

Отвечает за сцену и за подключение симулятора к ROS2. Кода-узлов почти не содержит; это описания
и запуск внешних процессов.

- **Миры** (`worlds/`): `follow_target.sdf` (один ходячий человек, эталон Фазы 3) и
  `follow_crowd.sdf` (три различимых человека с пересекающимися траекториями — сцена для проверки
  трекинга и идентичности).
- **Модели** (`models/`): вендорные копии актёров (`actor_target`, `actor_distractor_a/b`) с
  разным цветом одежды и ростом, и модель камеры `mono_cam` с наклоном вниз (~30°). Наклон
  устраняет «геометрическую стену»: горизонтальная камера теряла наземную цель на близкой
  дистанции.
- **`launch/sim.launch.py`**: поднимает два моста — **Micro-XRCE-DDS-Agent** (uORB PX4 → `/fmu/*`)
  и **`ros_gz_bridge`** (камера Gazebo → `/camera/image`, `/camera/camera_info` по конфигу
  `configs/simulator/camera_bridge.yaml`). Сам PX4 SITL запускается отдельным скриптом, не здесь.

### 4.3 `drone_perception` — зрение (`detector_node`)

Подписывается на `/camera/image`, извлекает из кадра одну сопровождаемую цель и публикует
`Target` (+ аннотированный кадр `/perception/image` для визуального контроля). Реализует
**двухуровневую логику захвата**:

- **Детекция и трекинг.** Кадр (переведённый в BGR) прогоняется через `model.track(persist=True)`
  — YOLOv8n с ByteTrack. Результат каждой детекции — `((x1,y1,x2,y2), класс, уверенность,
  track_id)`. Фильтр по классу `person` и по порогу уверенности.
- **Уровень 1 — быстрый путь (трекер).** Пока залоченный `track_id` виден в кадре, это наша цель;
  эмбеддинги не считаются (экономия GPU), эталон облика лишь изредка подпитывается.
- **Уровень 2 — идентичность (ReID), подсистема `reid/`.** Как только трек умирает, сверяется
  **каждый** кандидат с эталоном облика цели, и перезахват происходит **только** на прошедшего
  порог косинусной близости. Не прошёл никто → цель считается ненайденной (`detected=false`), и
  подмена другим человеком структурно невозможна. Компоненты (порт логики из project_1):
  - `embedder.py` — `ObjectEmbedder` на OpenCLIP ViT-B-32; вырезает фигуру и выдаёт эмбеддинг.
    Работает со скважностью (не каждый кадр) — эмбеддер делит GPU с YOLO и рендерингом. По
    умолчанию `reid.device: cuda`; при недоступности CUDA или ошибке загрузки модели (нехватка
    VRAM) автоматически откатывается на CPU. Режим можно принудительно задать ручкой
    `reid.device: cpu` в `configs/perception/detector.yaml`.
  - `target_identity.py` — `TargetIdentity`: «память облика» цели (роллинг-буфер эмбеддингов
    разных ракурсов, агрегация, порог косинуса). В отличие от многообъектного реестра оригинала,
    цель одна и **никогда не «протухает»** — дрон обязан искать своего сколько угодно долго.
  - `similarity.py` — косинусная близость (одиночная и батчевая).
  - Постоянный `object_id` присваивается при захвате облика и **не меняется** при перезахвате.
- **Оценка дистанции.** Pinhole-модель `d = f_y·H_real/h_px` со сглаживанием EMA; значению
  доверяем только если bbox целиком в кадре. `f_y` берётся из `camera_info` либо вычисляется из
  горизонтального FOV.
- **Оверлей (живые метрики, M6).** Поверх кадра рисуются все треки (залоченный выделен),
  дистанция, статус ReID, таймер «батареи» и строка `FSM | FPS | латентность инференса`.
  Состояние FSM и остаток батареи приходят от контроллера отдельными топиками (узлы не
  импортируют друг друга).

### 4.4 `drone_control` — управление (`follower_node`)

Ядро контура управления: непрерывный **offboard-цикл на 20 Гц**, который каждый тик публикует
уставки в PX4. Подписан на `Target` (от детектора) и на телеметрию PX4
(`/fmu/out/vehicle_local_position`, `/fmu/out/vehicle_status`).

**Каналы регулирования** (в момент, когда цель видна и достигнута рабочая высота):
- **Рыскание (yaw).** Пропорционально `offset_x` (с мёртвой зоной) — доворот на цель.
- **Дистанция (вперёд/назад).** По честной `distance_m` через **PID** (I убирает установившуюся
  ошибку сопровождения движущейся цели; при `ki=kd=0` вырождается в пропорциональный регулятор).
  Если честной дистанции нет — fallback на прокси площади. Особый случай: цель у нижнего края
  кадра (`offset_y` велик) → форсированный откат назад, чтобы не выпала из кадра.
- **Высота.** Пропорциональный регулятор к `target_altitude_m`; он же выполняет взлёт.
- Команда «вперёд» считается в body-frame и поворачивается в NED по текущему курсу.

**Конечный автомат (FSM).** Заменяет примитивное «нет цели → висеть»:

```
TAKEOFF ──(вышел на высоту)──► TRACK ──(цель видна)──► TRACK
   ▲                             │
   │                    (потеря цели)
   │                             ▼
   │                           HOLD ──(таймаут)──► LOST ──(таймаут)──► SEARCH
   │                             │                   │                   │
   └───────────── (перезахват того же object_id: → TRACK) ◄─────────────┘

                (безопасность: «батарея»/долгий SEARCH → RTL — терминально)
```

- **TAKEOFF** — набор рабочей высоты; горизонтального преследования нет.
- **TRACK** — активное сопровождение по каналам выше.
- **HOLD** — короткая пауза при потере: курс не меняем (чаще всего цель на пару секунд скрылась
  за другим человеком и вернётся туда же).
- **LOST** — доворот в сторону, где цель видели последней (вероятно, ушла за край кадра).
- **SEARCH** — медленное вращение на месте, **бессрочно**: ждём именно своего; ReID не пропустит
  чужого, поэтому искать можно сколь угодно долго.
- **RTL** — терминальное состояние: возврат домой отдан штатному режиму PX4, поток offboard
  глушится (иначе он перетянул бы режим обратно).

**Слой безопасности** (поверх FSM):
- **Geofence** — у границы гасится только радиальная (наружу) составляющая горизонтальной
  скорости; вдоль границы за целью двигаться можно (мягкий клэмп, без RTL).
- **Потолок высоты** — при достижении режется команда вверх.
- **«Батарея»** — таймер от арминга; по исчерпании → RTL (это имитация ресурса, не модель
  разряда).
- **Долгий SEARCH** — непрерывный поиск дольше таймаута → RTL (честный физический предел
  бессрочного поиска).

### 4.5 `drone_bringup` — сборка пайплайна

Не содержит логики, только **launch-файлы**, связывающие узлы. Главный —
`tracking_demo.launch.py`: поднимает `follower_node` и `detector_node` с их конфигами. Порядок
старта намеренный: контроллер стартует сразу (успевает заармиться и взлететь, пока нет
GPU-нагрузки), детектор — с задержкой `detector_delay_s` (тяжёлый инференс приходит позже) —
митигация тайминг-контеншна lockstep.

## 5. Поток информации и действий (сквозной)

### 5.1 Топики (каналы обмена)

| Топик | Тип | Направление |
|---|---|---|
| `/camera/image`, `/camera/camera_info` | `sensor_msgs/Image`, `CameraInfo` | Gazebo → detector |
| `/perception/target` | `drone_interfaces/Target` | detector → follower |
| `/perception/image` | `sensor_msgs/Image` | detector → просмотр (оверлей) |
| `/follower/state`, `/follower/battery_remaining_s` | `std_msgs/String`, `Float32` | follower → detector (для оверлея) |
| `/fmu/in/offboard_control_mode`, `/fmu/in/trajectory_setpoint`, `/fmu/in/vehicle_command` | `px4_msgs/*` | follower → PX4 |
| `/fmu/out/vehicle_local_position`, `/fmu/out/vehicle_status` | `px4_msgs/*` | PX4 → follower |

Топики `/fmu/*` используют QoS PX4 (best-effort, transient-local, глубина 1) — иначе телеметрия
не читается и команды не проходят.

### 5.2 Контур восприятия (30 Гц, темп камеры)

1. Gazebo рендерит кадр с камеры дрона → `ros_gz_bridge` публикует `/camera/image`.
2. `detector_node` прогоняет кадр через YOLO+ByteTrack.
3. Двухуровневый выбор цели: если залоченный `track_id` виден — быстрый путь; если трек умер —
   сверка кандидатов с эталоном облика (ReID) и перезахват того же `object_id`.
4. По bbox цели считаются нормализованные `offset_x/y`, `area_ratio` и pinhole-`distance_m`.
5. Публикуется `Target` (для контроллера) и `/perception/image` (оверлей для человека).

### 5.3 Контур управления (20 Гц, постоянный offboard-цикл)

Каждый тик, **независимо** от наличия цели:
1. Публикуется остаток «батареи» и текущее состояние FSM (для оверлея).
2. Если сработал фейлсейф (`RTL`) — цикл ничего больше не стримит (управление у PX4). Иначе:
3. Публикуется `OffboardControlMode` (заявка «управляю скоростью»).
4. Читается последняя телеметрия PX4; по высоте пересчитывается состояние FSM.
5. `_compute_setpoint()` возвращает `(vx, vy, vz, yaw_rate)` по каналам и текущему состоянию FSM.
6. Слой безопасности клэмпит уставку (geofence, потолок).
7. Публикуется `TrajectorySetpoint`.
8. Первые секунды: после прогрева потока уставок повторяются команды **переключить в offboard** и
   **заармить**, пока PX4 реально не перейдёт в ARMED+OFFBOARD.
9. Проверяются фейлсейфы («батарея», долгий SEARCH) → при срабатывании — терминальный RTL.

PX4 отрабатывает уставку скорости → крутит двигатели в Gazebo → аппарат смещается → камера видит
новый кадр → контур замыкается.

### 5.4 Последовательность запуска (что за чем оживает)

```
1. run_px4_sitl.sh   → Gazebo + PX4 SITL (физика, камера, автопилот)
2. sim.launch.py     → XRCE-агент (/fmu/*) + мост камеры (/camera/image)
3. tracking_demo     → follower_node (сразу: арминг+взлёт) + detector_node (с задержкой)
```

Затем: взлёт (TAKEOFF) → захват цели и подтверждение облика (TRACK) → сопровождение; при потере —
HOLD/LOST/SEARCH с перезахватом; по исчерпании «батареи» — RTL и посадка в точке старта.

## 6. Конфигурация и запуск

- **Конфигурация вынесена из кода** в `configs/` (принцип: «никаких магических чисел в коде»):
  `configs/perception/detector.yaml` (модель, порог уверенности, параметры трекинга, ReID,
  дистанции), `configs/control/follower.yaml` (коэффициенты регуляторов, лимиты скоростей, высота,
  параметры FSM и безопасности), `configs/simulator/*` (мост камеры, палитра актёров, стек).
- **Сборка — только `scripts/build.sh`** (colcon под python из venv), иначе узлы с pip-зависимостями
  (`torch`/`ultralytics`) падают с `ModuleNotFoundError`. Правка `.py`-узла требует пересборки
  (`ros2 launch` исполняет код из `install/`, не из `src/`); правка только `.yaml` — не требует.
- **Вспомогательные скрипты**: `run_px4_sitl.sh` (Gazebo+PX4), `run_xrce_agent.sh`, `stop_sim.sh`
  (гасит остатки процессов между прогонами), `setup_venv.sh` (окружение + прогрев весов ReID),
  `make_actor_variants.py` (генерация различимых актёров).
- **Аппаратные требования и версии стека** — `configs/simulator/stack.md`. На гибридной графике
  запуск обязателен с `GPU=nvidia`.

## 7. Границы и упрощения (важно для корректной интерпретации)

Система работает в симуляции, и ряд решений честен именно для неё:
- **«Батарея» — таймер, а не модель разряда.** Демонстрирует логику фейлсейфа, не энергетику.
- **Дистанция предполагает известный рост цели.** Для follow-me одного класса это допустимо; при
  смене роста актёра параметр `h_real_m` нужно синхронизировать.
- **ReID в этой сцене вырождается в цвет и геометрию.** Меши плоскозакрашены, без текстур; выводы
  о качестве ре-идентификации не переносятся на реальное видео без проверки.
- **Возврат домой отдан штатному RTL PX4** — это близко к реальной эксплуатации, но остановиться
  и вернуться в сопровождение из RTL система не может (состояние терминальное).

Полный журнал реализации с диагнозами и найденными ловушками — `docs/phase4_setup.md` §8.
