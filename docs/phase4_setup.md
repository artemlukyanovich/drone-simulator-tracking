## 1. Цель Фазы 4

Превратить рабочий MVP-follower в **устойчивый трекер, приближённый к полевым условиям**.
Проверяемая формулировка цели: в сцене с **несколькими** ходячими людьми дрон
- выбирает и **удерживает одного** (не «перепрыгивает» на чужого при пересечениях),
- при потере цели **активно ищет и переловывает** её, а не просто зависает,
- держит дистанцию по **честной оценке** (не по грубому прокси площади),
- ведёт себя **безопасно** (границы, фейлсейфы) и оставляет **измеримый след** (метрики, графики).

```
Gazebo камера → /camera/image
  → detector_node (YOLO + ByteTrack)  → /perception/target (+ track_id, distance_m)
                                       → /perception/image  (оверлей: все ID, залоченный, дистанция, FSM, FPS)
  → follower_node (FSM + PID offboard) → setpoints / RTL в PX4
                                       → outputs/telemetry/*.csv  (ошибка, дистанция, ID-свитчи, латентность)
  → PX4 SITL → моторы в Gazebo
```

## 2. Принятые решения Фазы 4 (с обоснованием)

| # | Решение | Почему так |
|---|---------|-----------|
| Ф4-1 | **Трекер — ByteTrack, встроенный в ultralytics** (`model.track(persist=True)`), а не отдельный DeepSORT/BoT-SORT-пакет. | `track_id` «из коробки», ноль новых зависимостей, детерминированный ID между кадрами. BoT-SORT с ReID-эмбеддингами (устойчивее к длинным перекрытиям) — **запасной вариант**, включаем только если ByteTrack теряет ID на пересечениях (Ф4-риск R1). Начинаем с простого. |
| Ф4-2 | **Политика захвата: lock-on-один-track_id.** Стартовый выбор — крупнейший bbox (ближайший человек); далее держим **именно этот id**, игнорируя прочих. Смена цели — только по правилу «потеря + таймаут» (см. FSM). | Это ядро «follow-me в толпе». Без явного lock детектор каждый кадр выбирал бы «лучшего» и дрон метался бы между людьми. Крупнейший bbox = разумная эвристика «кого сопровождаем» (ближайший/по центру); позже можно заменить на выбор кликом/по атрибуту. |
| Ф4-3 | **Расширяем `Target.msg`, не ломая Фазу 3:** добавляем `int32 track_id` и `float32 distance_m`. Существующие поля (`detected`, `offset_x/y`, `area_ratio`) сохраняются. | Обратная совместимость: follower Фазы 3 продолжит работать по старым полям. `track_id` = кого ведём; `distance_m` = честная дистанция (Ф4-5). `area_ratio` остаётся как fallback и для сравнения «прокси vs честная». Состояние FSM в сообщении цели **не** держим — это забота follower, не детектора (разделение ответственности, ср. Ф3-4). |
| Ф4-4 | **Камера смотрит вниз (наклон ~30°), сначала статически** в SDF дрона; активный gimbal-joint (отдельный канал по `offset_y`) — второй шаг/опция. | Снимает «геометрическую стену» 4B (Ф3-7): горизонтальная камера на 2.5 м теряла наземную цель ближе ~3 м. Наклон вниз возвращает цель в кадр на близкой дистанции → работают вертикальный канал и честная оценка. Статический наклон — минимальное изменение с максимальным эффектом; активный gimbal усложняет и оставлен как улучшение. |
| Ф4-5 | **Дистанция по pinhole-модели:** `distance_m ≈ f_y · H_real / h_px`, где `H_real≈1.7 м` (рост actor'а), `h_px` — высота bbox в пикселях, `f_y` — фокус из intrinsics камеры. Считаем в **detector_node** (у него пиксели). | `area_ratio ~ 1/d²` — нелинейный и слабый прокси (из-за него в 4B пришлось задирать `kp_forward` до 18 и ловить крошечные ошибки). Pinhole даёт **линейную по 1/h_px** метрику в метрах → P/PID forward-канала настраивается физично, `area_target` (доля кадра) заменяется на `distance_target` (метры). Допущение «известный рост» честно для follow-me одного класса и документируется. |
| Ф4-6 | **P → PID** на forward и yaw: интеграл с anti-windup (клэмп), D по фильтрованной производной. Коэффициенты `ki_*`,`kd_*` в `follower.yaml`, по умолчанию **0** → идентично Фазе 3. | I убирает статическую ошибку удержания дистанции, D гасит раскачку на резких манёврах цели. Дефолт-0 = безопасный откат к проверенному P; включаем и тюним инкрементально. Опц. **feedforward** по оценке скорости цели (из разницы позиций track_id между кадрами) — упреждение, если PID отстаёт от быстрой цели. |
| Ф4-7 | **Конечный автомат (FSM) в follower_node:** `TAKEOFF → SEARCH → TRACK → LOST → (REACQUIRE) → TRACK`; `LOST` дольше таймаута → `RTL/LAND`. | Заменяет «нет цели → hover». `SEARCH` — доворот/подъём для обзора; `TRACK` — PID-слежение за залоченным id; `LOST` — доворот в сторону последнего known-offset, пытаясь снова увидеть **тот же** id (ReID-lite по позиции; при BoT-SORT — по эмбеддингу). Явные состояния = предсказуемое, презентабельное поведение и место для фейлсейфов. |
| Ф4-8 | **Слой безопасности/failsafe** поверх FSM: geofence по радиусу от точки старта, max altitude (мягко — не выдаём setpoint за пределы), `LOST`-таймаут и sim-«батарея» (таймер) → команда **RTL** в PX4 (`vehicle_command`). | Полевой дрон без границ и возврата недопустим. Geofence/altitude проверяем в follower (мягкий клэмп setpoint), возврат отдаём штатному режиму PX4 RTL — честно и близко к реальной эксплуатации. Читается как production-readiness. |
| Ф4-9 | **Телеметрия и дашборд:** follower/detector пишут CSV в `outputs/telemetry/` (git-ignored, §7 CLAUDE.md); `scripts/plot_telemetry.py` (matplotlib) → графики в `outputs/`; на `/perception/image` — **оверлей** (все track_id, залоченный выделен, дистанция, состояние FSM, FPS/латентность). Опц. `rosbag record`. | Делает демо **количественным** — то, что смотрят в портфолио: ошибка слежения во времени, дистанция, число ID-свитчей, латентность детектора. Оверлей = визуальное доказательство трекинга и совмещение демо-акцентов M1×M6. |
| Ф4-10 | **Отдельный мир `worlds/follow_crowd.sdf`** с 2–3 ходячими actor'ами и пересекающимися траекториями; `follow_target.sdf` (4B) **не трогаем**. | Дистракторы — суть проверки трекинга (без них ID-логика не демонстрируется). Отдельный файл сохраняет воспроизводимость 4B как регресс-эталона. Траектории строим по уроку Ф3-6 (смещать от точки старта дрона, иначе спин) и с явными пересечениями (стресс для ByteTrack). |
| Ф4-11 | **Строгий лок: захваченную цель НИКОГДА не подменяем другим человеком.** Не нашли своего → дрон **бессрочно ищет именно его** (SEARCH), а не продолжает миссию с чужим. Выход из бессрочного поиска по таймауту (RTL/посадка) — забота M5, не M2. | Требование пользователя (2026-07-18) и правильная полевая семантика: дрон отправлен сопровождать **конкретного** человека. Сопровождение не того — отказ хуже отказа от задачи: он незаметен оператору и уводит аппарат не туда. Принимаем цену: после долгой потери прогон может закончиться вращением — это **корректное поведение, а не баг**. |
| Ф4-12 | **Все ходячие объекты визуально различимы между собой** (у каждого свой облик), а не «цель vs одинаковый фон». Реализация: вендорные копии меша `Mingfei/actor/walk.dae` в `src/drone_simulator/models/` с разными `<diffuse>` у материалов `sweater-*`/`jeans-*` **+ разные ростовки** (`<scale>`); в мире Fuel-URL заменяется на локальные пути. | Меш **не текстурирован** — цвета лежат прямо в COLLADA именованными материалами (`sweater-green`, `jeans-blue`, `skin-mat`), поэтому перекраска = правка одного тега: без графики, оффлайн, воспроизводимо. Механизм вендоринга уже проверен на `mono_cam` (M3): `GZ_SIM_RESOURCE_PATH` из `run_px4_sitl.sh` затеняет внешние модели, git-ignored код PX4 не трогаем. Различие **всех** объектов между собой обязательно: гейт идентичности должен уметь отвергать *конкретного похожего*, а не «всё, что не цель». Разный рост — вторая, независимая от цвета ось различия (см. Ф4-13). |
| Ф4-13 | **Ре-идентификация — порт ReID-стека из project_1, а не самодельный гейт.** Переносим логику `ObjectCropper → ObjectEmbedder` (OpenCLIP ViT-B-32) → `ObjectMemory` (галерея, cosine-порог, роллинг-буфер эмбеддингов) → `ReIDManager`. **Лок ставится на `object_id`, а не на `track_id`.** Не сошлось → отказ → остаёмся в SEARCH (Ф4-11). | `track_id` временный (умирает с треком), `object_id` — постоянный, переживает окклюзию и смену `track_id` (`project_1/docs/embeddings_reid.md`). Ф4-11 — задача **идентичности**, а не ассоциации, поэтому нужна именно галерея. Прямо реализует решение Р3 плана (перцепция из project_1 переносится в ROS2-ноды как логика) — здесь это не переиспользование ради галочки, а буквально нужный модуль. |
| Ф4-14 | **BoT-SORT `with_reid` нашу задачу НЕ решает** — из запасного пути (R1) исключается как основной ответ. Он остаётся опцией «сделать треки живучее», но не заменяет галерею. | Эмбеддинг в BoT-SORT работает **внутри ассоциации трекера**, горизонт — пока жив трек: истёк `track_buffer` → id потерян навсегда, памяти «кого мы сопровождаем» у трекера нет. Записано явно, чтобы не возвращаться к этому спору. |
| Ф4-15 | **Переносим логику ReID, но НЕ режим её работы:** эмбеддер дёргаем с низкой скважностью — на захвате цели и далее только на кандидатах при потере; не на всех треках и не каждый кадр. Веса ViT-B-32 (~350 МБ) — в кэш Torch Hub, в git не идут; `open-clip-torch` → `requirements.txt`. | project_1 эмбеддит каждый трек каждый кадр — там это офлайн-видео. У нас на одной видеокарте одновременно рендер Gazebo + YOLO, и контеншн **уже однажды ронял арминг** (§9 phase3, `GPU=nvidia`). Это риск R4, поэтому скважность — не оптимизация, а условие работоспособности. |
| Ф4-16 | **ОТМЕНЁН ростовой признак в формулировке «`H = d·h_px/f_y`» (был частью Ф4-13).** Он **циклический** и тождественно ничего не измеряет. Настоящая оценка роста возможна, но через **геометрию земли**: `d_ground = h_cam/tan(θ_ног)` по строке пикселей с ногами (нужны высота дрона из PX4 и калиброванный наклон камеры), и уже `H = d_ground·h_px/f_y`. Отложено отдельной задачей, в 7A не входит. | Найдено при реализации 7A (2026-07-18): дистанция `d` у нас сама считается как `f_y·H_real/h_px` (M3), поэтому подстановка даёт `H = H_real` — константу из конфига. Признак выглядел независимым, но им не был. Записано явно, чтобы «добавить рост в гейт» не всплыло снова как «дешёвая идея». Версия через плоскость земли рост НЕ использует и потому честна, но требует подписки детектора на телеметрию и ломается при перекрытых ногах — отсюда отдельная задача. Ростовки actor'ов из 7-0 не пропали: разные силуэт и пропорции в кадре видит сам эмбеддинг. |
| Ф4-17 | **Веса ReID прогреваются заранее в `scripts/setup_venv.sh`**, а не качаются на старте ноды. Имя модели скрипт читает из `configs/perception/detector.yaml` (не дублируем значения). Прогрев не критичен: не удался → предупреждение, ReID отключится сам. Отключается через `PREWARM_REID=0`. | `ObjectEmbedder` грузит OpenCLIP **синхронно в конструкторе** `detector_node`. Без прогретого кэша ~350 МБ качаются уже на старте прогона, а `follower_node` к этому моменту армится и взлетает → цели нет → FSM уходит в `SEARCH`, и дрон **крутится на месте всю загрузку**. Снаружи неотличимо от поломки. Проблема разовая и относится к развёртыванию, поэтому лечится в установке окружения, а не усложнением ноды потоком фоновой загрузки (вариант рассматривался и отклонён как преждевременный). На машине разработки не проявлялась — веса лежали в кэше HF от project_1, что и маскировало ловушку от нас самих.  |

## 3. Изменения интерфейса (`drone_interfaces/Target.msg`)

Добавляемые поля (в конец — ABI-совместимо для сборки, старые потребители не ломаются):

```
int32   track_id     # id залоченной цели от трекера (-1 = нет/не назначен)
float32 distance_m    # оценка дистанции до цели, метры (pinhole, Ф4-5); 0 = нет оценки
```

`area_ratio` сохраняется (fallback + сравнение). После правки `.msg` — **обязательна пересборка**
`drone_interfaces` через `scripts/build.sh` (venv-shebang, §12 phase3) и `source install/setup.bash`.

## 6. Проверка и визуализация

### Когда пересобирать (ОБЯЗАТЕЛЬНО перед проверкой)

`ros2 launch` запускает код из `install/`, **не из `src/`**. Поэтому **любая правка `.py`-кода
ноды не действует, пока пакет не пересобран** — в прогоне будет крутиться старая версия, а правка
«не появится» (типовая ловушка: 2026-07-21 не показывался таймер батареи — код был верным, но
пакет `drone_perception` не пересобран). Правило:

| Что изменилось | Нужна пересборка? | Что делать |
|---|---|---|
| `.py`-код ноды (`follower_node`, `detector_node`, `reid/*`, …) | **ДА** | `scripts/build.sh --packages-select <пакеты>` |
| `.msg` в `drone_interfaces` | **ДА** (+ `source install/setup.bash` заново) | `scripts/build.sh` |
| `package.xml` / `setup.py` | **ДА** | `scripts/build.sh --packages-select <пакет>` |
| только `.yaml` в `configs/` | **нет** | launch читает конфиг из `configs/` напрямую |
| только SDF/ассеты мира | **нет** | меняется лишь сцена Gazebo |

Собирать **только `scripts/build.sh`** (colcon под venv-python, §12 phase3 — иначе ноды с
`torch`/`ultralytics` падают `ModuleNotFoundError`), НЕ голым `colcon build`. Пример — пересобрать
контроллер и детектор после правки их нод:
```bash
scripts/build.sh --packages-select drone_control drone_perception
```
**Проверить, что сборка взяла, ДО запуска sim** — grep по установленной копии на характерный
токен правки (обе/все цифры должны стать `>0`):
```bash
grep -c <токен_правки> install/<pkg>/lib/python3.10/site-packages/<pkg>/<node>.py
```
Пере-`source` для python-правок не нужен (пути install не меняются), нужен только после правки
`.msg`. После сборки — обычный перезапуск (`scripts/stop_sim.sh` → 3 терминала).

### Запуск и наблюдение

Терминальная подготовка и запуск sim — как в Фазе 3 (`phase3_setup.md` §10; `GPU=nvidia`
обязателен, §9; детектор — с `detector_delay_s`, Ф3-8). Sourcing нужен в ROS2-терминалах, но не в
терминале PX4/Gazebo (подробности и полный набор команд — §8, блок проверки M3).
**Между прогонами обязателен `scripts/stop_sim.sh`**: в standalone PX4 не владеет Gazebo, и после
`shutdown` живыми остаются gz-сервер/GUI, XRCE-агент и мосты — недобитые процессы дают
`Arming denied`, молчащую камеру и дубли топиков. Он же — аварийный выход при упавшем запуске.
Специфика Фазы 4:
- **M1:** `ros2 topic echo /perception/target` — смотреть, что `track_id` стабилен для ведомого
  и не перескакивает; на `/perception/image` (rqt_image_view) — все боксы с id, залоченный выделен.
- **M3:** сравнить `distance_m` с реальной дистанцией `dron↔actor` (позы из Gazebo `gz topic`/`/fmu`).
- **M2/M4:** спровоцировать потерю (увести за препятствие) и резкий манёвр цели, наблюдать FSM/плавность.
- **M5:** искусственно вытолкнуть setpoint за geofence и промотать «батарею» → ожидать RTL.
- **M6:** `python scripts/plot_telemetry.py outputs/telemetry/<run>.csv` → графики; запись демо.

## 7. Риски и открытые вопросы Фазы 4

- **R1 — ByteTrack теряет id при длинных перекрытиях/выходе из кадра.** Митигация (уточнена
  2026-07-18): не BoT-SORT — он лечит ассоциацию, а не идентичность (Ф4-14). Лечим галереей ReID
  из project_1 и локом на `object_id` (Ф4-13); дополнительно — увеличенный `track_buffer` в своём
  `configs/perception/bytetrack.yaml`, чтобы короткие перекрытия вообще не доходили до перезахвата,
  и поднятый `conf` против лавины «мерцающих» треков от дальних дистракторов (см. §8, ловушка M1).
- **R6 — рост цели теперь параметр идентичности И дистанции.** Ф4-12 делает actor'ов разного
  роста → `h_real_m` в `detector.yaml` перестаёт быть универсальным: pinhole-дистанция (M3) должна
  считаться по росту **залоченной цели**. При смене ростовок в мире — синхронно править `h_real_m`,
  иначе тихо поедет вся дистанция и с ней forward-канал.
- **R7 — в этой симуляции любой дескриптор вырождается в цвет+геометрию.** Меши плоскозакрашенные,
  без текстур; три actor'а — один меш. Даже обученный эмбеддинг здесь сравнивает по сути одежду.
  Поэтому Ф4-12 обязателен, а выводы о качестве ReID **не переносим** на реальное видео без проверки.
- **R2 — `distance_m` шумит** при неполном bbox (человек частично за кадром/препятствием). Митигация:
  сглаживание (EMA/медиана), доверять только при `detected && bbox целиком в кадре`; иначе fallback на `area_ratio`.
- **R3 — активный gimbal vs фиксированный наклон.** Решаем по итогу инкремента 6: если фиксированного
  наклона хватает для удержания цели во всём диапазоне дистанций — активный gimbal не делаем.
- **R4 — производительность:** трекинг + оверлей + несколько actor'ов + рендер на гибридной графике.
  Держать `GPU=nvidia`; при просадке FPS — уменьшить разрешение детекции/частоту (замерять латентность, M6).
- **R5 — sim-«батарея»/RTL как имитация.** Это упрощение (не реальная модель разряда PX4); документируем
  как демонстрацию логики фейлсейфа, не как точную энергетику.

## 8. Журнал реализации

### Инкремент 5 (M1) — мультитрекинг + захват цели. Ядро принято 2026-07-15.

**Сделано.** `Target.msg` +`track_id`/`distance_m` (в конец, ABI-совместимо). `ObjectDetector`
→ режим `model.track(persist=True, tracker=bytetrack.yaml)`, детекция стала 4-кортежем с
`track_id` (зависимость `lap` — в `requirements.txt`). `detector_node`: политика lock (Ф4-2) —
захват крупнейшего подтверждённого трека, далее держим его id; потеря id в кадре →
`detected=false`. Мини-оверлей: все боксы с id, залоченный выделен. Новый мир
`worlds/follow_crowd.sdf` — 3 actor'а (цель + 2 фоновых дистрактора, разные периоды 72/60/54 с →
плывущие пересечения); `follow_target.sdf` не тронут. Диаг-лог `dets/ids/locked/matched` за
флагом `debug_tracking` (по умолчанию off). `follower_node` и топики не менялись.

**Как проверить (воспроизвести гейт).** Запуск как для M3 выше (мир `follow_crowd.sdf`,
`GPU=nvidia`, `detector_delay_s:=8`). Для разбора трекинга — поднять флаг:
```
ros2 launch drone_bringup tracking_demo.launch.py detector_delay_s:=8 \
  detector_config:=<копия detector.yaml с debug_tracking: true>
```
(или временно `debug_tracking: true` в `configs/perception/detector.yaml`). Критерии:
- `ros2 topic echo /perception/target` → `track_id` стабилен у ведомого, не скачет на пересечениях;
- в `/perception/image` все люди в боксах с id, залоченный выделен красным/толстым, прочие синим;
- дрон ведёт ОДНОГО, не перепрыгивает на дистрактора при проходе того по азимуту цели;
- с `debug_tracking:=true` — лог `dets/ids/locked/matched` (потеря id → `matched=False`, это ожидаемо, лечится M2).

**Что показал прогон (2026-07-15, `follow_crowd.sdf`, `debug_tracking:=true`).**
- ✅ **Ядро трекинга работает:** захват `id=1` (крупнейший), дрон довернулся и вёл цель ~38 с
  подряд (`locked=1 matched=True`), удерживая `offset_x≈0`. Дистракторы были в кадре
  (`ids=[1,9,44,92]`), но лок **ни разу не перескочил** на них — это и есть проверяемая суть M1.
- ❌ **Где рвётся:** на ~38 с цель на миг выпала из кадра/была перекрыта → ByteTrack удалил трек
  `1` и при повторной детекции выдал **новый** id (`290`). Политика «держать id вечно без
  перезахвата» не восстанавливается → `matched=False` навсегда → дрон завис. id доросли до 775
  (сильная текучесть треков от дальних дистракторов на грани `conf`).

**Диагноз (данные однозначны).** Это стык двух вещей: **R1** (ByteTrack переназначает id после
перекрытия/выхода из кадра) и **геометрической стены Ф3-7** — на захвате `offset_y≈0.32`, т.е.
цель у нижнего края кадра: горизонтальная камера на 2.5 м периодически роняет наземную цель из
кадра → детекция рвётся → id теряется.

**Решение (согласовано с пользователем 2026-07-15): «принять ядро M1, идти в M3».** Захват+не-
перескок — показаны, это выигрыш трекинга. Полное «удержание при потере» **не** чиним re-lock'ом в
M1 (это дублировало бы M2): корневой триггер потери снимает **M3** (наклон камеры вниз убирает
дропаут по низу кадра), а перелов **того же** id — **M2** (REACQUIRE, Ф4-7). Решение Ф4-2 «detected=
false при потере, смена цели — правилом потеря+таймаут в FSM» остаётся в силе; сам re-lock живёт в
M2, не в M1. Гейт M1 закрывается по факту «ведёт одного, не прыгает на чужих»; сквозная
непрерывность придёт после M3+M2.

**Ловушка на будущее (M3/M4).** Дальние дистракторы мерцают на грани `conf=0.5` → лавина новых
track_id. Если это зашумит перелов в M2 — поднять `conf`, увеличить `track_buffer` ByteTrack
(кастомный tracker-yaml в `configs/`) или ограничить детекцию по площади/зоне. Пока не трогаем.

### Инкремент 6 (M3) — наклон камеры + честная дистанция + вертикаль. Принят 2026-07-15.

**Сделано.** Камера наклонена вниз ~30°: вендорная копия модели PX4
`src/drone_simulator/models/mono_cam/model.sdf` (сенсор `pose … 0 0.52 0`), которую
`run_px4_sitl.sh` кладёт первым в `GZ_SIM_RESOURCE_PATH` → затеняет PX4-шный `mono_cam`, внешний
код не трогаем. `detector_node`: `distance_m = f_y·H_real/h_px` (Ф4-5), `f_y` из
`/camera/camera_info` или вычисляется из `horizontal_fov`+ширины (fallback, оказался основным —
см. ниже), EMA-сглаживание, доверие только при полном bbox в кадре (R2); дистанция в оверлее у
залоченного бокса. `follower_node`: forward-канал по `distance_target_m` (метры) с естественным
откатом назад при `distance < target` + guard по `offset_y` (цель у нижнего края → откат);
area-прокси остался fallback'ом. Новые параметры — в `detector.yaml`/`follower.yaml`.

**Как проверить (воспроизвести гейт).** Запуск как в Фазе 3 (`GPU=nvidia` обязателен;
`detector_delay_s:=8` против стартовой гонки рендера). **Подготовка окружения нужна в
ROS2-терминалах (2, 3 и просмотр), но НЕ в терминале 1** — `run_px4_sitl.sh` запускает только
`gz sim` + `make px4_sitl`, это процессы Gazebo/PX4, а не ROS2-ноды, и ROS-окружения им не надо
(уточнено 2026-07-18 по факту; ранее здесь ошибочно стояло «в каждом терминале»). В ROS2-терминалах
— активный `.venv` + оба source, иначе `ros2`/ноды не найдутся:
```
source /opt/ros/humble/setup.bash && source install/setup.bash    # терминалы 2, 3, просмотр; из корня проекта
```
По терминалам:
```
Терминал 1: WORLD=src/drone_simulator/worlds/follow_crowd.sdf GPU=nvidia scripts/run_px4_sitl.sh   # без source
Терминал 2: ros2 launch drone_simulator sim.launch.py
Терминал 3: ros2 launch drone_bringup tracking_demo.launch.py detector_delay_s:=8
Просмотр:   ros2 run rqt_image_view rqt_image_view /perception/image   # НЕ голый rqt_image_view — его нет в PATH
```
⚠️ **Между прогонами — `scripts/stop_sim.sh` (обязательно).** В standalone-режиме PX4 **не владеет**
Gazebo, поэтому `pxh> shutdown` гасит только автопилот, а gz-сервер/GUI, XRCE-агент и мосты
остаются жить. Недобитые процессы прошлого прогона — типовая причина «необъяснимых» отказов:
`Arming denied`, молчащий `/camera/image`, дубли топиков (§Фаза 3 §10/§13). Скрипт гасит
`gz sim` / `bin/px4` / `MicroXRCEAgent` / `parameter_bridge` и печатает, что осталось.
Годится и как аварийный выход, если терминал закрыли не по-людски или запуск упал на середине.
Перед стартом стоит убедиться, что чисто:
```
scripts/stop_sim.sh                                            # погасить всё от прошлого прогона
pgrep -af "gz sim|bin/px4|MicroXRCEAgent|parameter_bridge"      # ожидаемо: пусто
```
Критерии (глазами по `/perception/image` и `ros2 topic echo /perception/target`):
- камера смотрит вперёд-вниз, цель в кадре целиком, из нижнего края вблизи НЕ выпадает (наклон);
- на залоченном (красном) боксе подпись дистанции `~X.Xm`, не `d=?`; при слежении ~4.6–4.8 м;
- в `echo` поле `distance_m` живое (не 0), `detected/track_id` осмысленны;
- цель подходит близко → дрон отходит НАЗАД, удерживая её в кадре (откат).

**Что показал прогон (2026-07-15).**
- ✅ **Наклон снял стену 4B:** камера смотрит вперёд-вниз, цель держится в кадре, из нижнего края
  вблизи не выпадает. Дрон следует за идущим человеком.
- ✅ **Откат назад работает** при сближении (естественно из ошибки дистанции).
- ✅ **Честная дистанция в кадре:** оверлей стабильно показывает ~4.6–4.8 м при слежении (уставка
  `distance_target=4.0`; расхождение — динамическое отставание от идущей цели, ожидаемо). Значение
  физически согласовано (при 4.7 м и росте 1.7 м bbox ~98 px из 480 — ровно геометрия pinhole).

**Ловушка: `camera_info` не дошёл до детектора** (`distance_m` держался 0, оверлей `d=?`). Причина
точечно не копалась — вместо зависимости от топика `f_y` считается из известных `horizontal_fov`
(1.74) и ширины кадра: `f_y=(width/2)/tan(hfov/2)≈270 px`. Это надёжнее (нет внешней зависимости) и
сразу дало рабочую дистанцию; `camera_info` оставлен как необязательное уточнение.

**Про сверку точности (осознанное решение).** Планировалась независимая сверка `distance_m` с
позами Gazebo (±10–15%). На практике это утонуло: `ros_gz_bridge` для `Pose_V→TF` теряет имена
сущностей (берёт их из `header.data`, а не из поля `name` → все `child_frame_id` пустые), а
`gz topic -e` в пайп/файл буферизует вывод и теряет его на Ctrl-C. Решено **не тратить время** на
лабораторную сверку: метрика школьная (pinhole), `f_y` проверяем, значение правдоподобно и
устойчиво, грубого вранья нет. Гейт «честная дистанция» закрыт рабочей метрикой в кадре.
Диагностические `check_distance.py`/`run_pose_bridge.sh` удалены как нерабочие. Если позже
понадобится точная валидация — делать через именованный источник поз (напр. PosePublisher на
actor'ах), не через `Pose_V→TF`.

### Инкремент 7-0 — различимые actor'ы (подготовка к ReID). Принят 2026-07-18.

**Сделано.** Три actor'а `follow_crowd.sdf` получили собственный облик (Ф4-12) по двум
независимым осям: цвет одежды (свитер и джинсы **порознь** — чтобы гейт не ломался на «похожей
гамме») и рост через `<skin><scale>`. Реализация — вендорные копии меша в
`src/drone_simulator/models/actor_{target,distractor_a,distractor_b}/`; мир ссылается на
`model://actor_*`, Fuel-URL из мира ушли полностью.

| Actor | Свитер | Джинсы | scale | Рост |
|---|---|---|---|---|
| `target_person` | красный | тёмно-синие | 1.0 | ~1.7 м |
| `distractor_1` | жёлтый | тёмно-зелёные | 0.92 | ~1.56 м |
| `distractor_2` | голубой | светло-серые | 1.08 | ~1.84 м |

Перекраска возможна потому, что меш Fuel **не текстурирован**: цвета лежат прямо в COLLADA как
`<diffuse>` именованных материалов (`sweater-green-effect`, `jeans-blue-effect`). Генератор —
`scripts/make_actor_variants.py`, палитра/ростовки — `configs/simulator/actor_variants.yaml`
(§7 CLAUDE.md: числа не в коде). Правятся ровно 2 материала из 6 — кожа и глаза не тронуты.
Заодно по запросу поднята скорость цели: период круга 72→50 с (0.22→**0.31 м/с**, +44%);
50 с выбрано некратным периодам дистракторов (60/54), иначе пересечения повторялись бы в одной
фазе и стресс-тест выродился бы.

**Решения по реализации.** (1) Сгенерированные меши **коммитятся** (3×2.2 МБ), а не собираются на
лету: сцена не зависит от прогретости чужого кэша Fuel и нет ловушки порядка запуска; скрипт
оставлен для воспроизводимости и повторной перекраски. (2) У цели `scale=1.0` **намеренно** — её
рост есть база pinhole-дистанции M3, поэтому `h_real_m: 1.7` остаётся верным и **M3 ретюна не
требует** (риск R6; предупреждение продублировано в конфиге и в мире).

**Как проверить.** Запуск как для M3 выше (мир `follow_crowd.sdf`). Пересборка не нужна —
менялись только ассеты. Критерии: (1) в Gazebo три человека разного цвета и роста; (2) **цвета
читаются на `/perception/image`** — это главное, ReID будет работать с картинкой камеры, а не с
видом Gazebo; (3) регресс M1/M3 цел — захват, слежение, дистанция ~4.6–4.8 м.

### Инкремент 7A (M2) — идентичность цели + FSM поиска. ПРИНЯТ 2026-07-18.

**Сделано — перцепция.** Порт ReID-стека project_1 в новый подпакет
`src/drone_perception/drone_perception/reid/` (Ф4-13, решение Р3):
- `embedder.py` — `ObjectEmbedder` (OpenCLIP ViT-B-32) + `crop_bbox`. Отличия от оригинала:
  кроппер свёрнут до одной функции (нам нужен кроп на кандидата, а не словарь по всем трекам

- `similarity.py` — косинус, перенесён почти дословно. `find_best_match` не перенесён: он искал

- `target_identity.py` — `TargetIdentity`: роллинг-буфер обликов + агрегация (mean/ema/recent/

`detector_node` стал двухуровневым: пока трекер ведёт цель — дешёвый путь по `track_id`, без
эмбеддингов; трек умер — сверка КАЖДОГО кандидата с эталоном облика и перезахват **только** на
прошедшего порог. Не прошёл никто → `detected=false` → дрон ищет дальше. Подмена цели чужим
структурно невозможна: без порога кандидат не возвращается вообще. Эталон подпитывается редкими
свежими ракурсами (человек поворачивается, вид со спины ≠ анфас) + дозахват, если на самом
захвате кроп был негоден. На `/perception/image` — статус: `LOCKED (свой)` / `ИЩУ СВОЕГО
(лучший 0.xx)` / `ReID: OFF`.

**Сделано — управление.** FSM в `follower_node` (Ф4-7): `TAKEOFF → TRACK → LOST → SEARCH → TRACK`.
`LOST` — короткий (`lost_hold_s`) доворот в сторону последнего `offset_x`: чаще всего цель просто
ушла за край кадра. `SEARCH` — медленное вращение на месте, **бессрочно** (Ф4-11); выход в RTL по
таймауту — это M5, не здесь. Горизонтальная скорость в обоих состояниях ноль: искать вслепую
перемещением опасно и бессмысленно.

**Проверено автоматически (до симуляции).** Гейт идентичности на векторах: свой → принят,
ортогональный → `None`, из смеси выбран правильный. FSM прогнана с фейковой телеметрией:
`TAKEOFF → TRACK` (vx=+1.0, yaw=+0.60 к цели справа) `→ LOST` (yaw=+0.35 в сторону последнего
появления) `→ SEARCH` (вращение продолжается) `→ TRACK` при возврате. Обе ноды поднимаются с
новыми параметрами, `cv_bridge` цел (`numpy 1.26.4` — фиксация `numpy<2` пережила установку
`open-clip-torch`). Веса ViT-B-32 нашлись в кэше HF от project_1 → загрузка ReID ~2 с.

**Порог `similarity_threshold: 0.90` — ОЦЕНКА, а не измерение.** На синтетических фигурах в
цветах наших актёров: свой при смене освещения **0.999**, чужие **0.815–0.871**. Порог лёг между

между баллом СВОЕГО при возврате и баллами дистракторов.

- **порог ReID** `similarity_threshold: 0.90` не тюнился по реальным баллам; `reid.debug: true`
  печатает балл по каждому кандидату, если поведение перезахвата окажется капризным.
- **дежурная ловушка запуска.** Иногда Терминал 1 не доходит до `Ready for takeoff` и далее
  сыплет `Arming denied: Resolve system health failures first`. По §9 `phase3_setup.md` это НЕ
  контеншн GPU (`GPU=nvidia` на эту строку не влияет), а чаще всего недобитые процессы прошлого
  прогона → `scripts/stop_sim.sh` + `pgrep -af "gz sim|bin/px4|MicroXRCEAgent|parameter_bridge"`
  (пусто); точную причину показывает `commander check` в `pxh>`. Предложение добавить в

### Инкремент 7B (M4) — PID канала дистанции. ПРИНЯТ 2026-07-18.

**Что и зачем.** Чистый P физически не сводит ошибку к нулю за ДВИЖУЩЕЙСЯ целью: чтобы дрон ехал
со скоростью цели, член `kp·e` обязан быть ненулевым, значит и ошибка обязана быть ненулевой.
При `v_цели≈0.31` м/с (после ускорения актёра в 7-0) и `kp_distance=0.5` равновесие приходится на
`e = 0.31/0.5 ≈ 0.62` м — это ровно наблюдавшиеся **4.6–4.8 м при уставке 4.0**. Модель канала,
прогнанная численно, дала 4.62 м, что совпало с фактом и подтвердило диагноз. Интеграл берёт
постоянную составляющую скорости на себя: когда `e→0`, накопитель не обнуляется и продолжает
выдавать нужные 0.31 м/с, а P занимается только отклонениями.

**Сделано.** `_distance_pid()` в `follower_node`: `kp·e + ki·∫e·dt + kd·de/dt` с зажимом
накопителя (`i_limit_distance`) и `_reset_pid()`. Сброс происходит (1) при любом состоянии FSM
кроме `TRACK` — за время `HOLD/LOST/SEARCH` ошибка не обновляется, и сохранённый интеграл дёрнул
бы дрона вперёд сразу после перезахвата (стык M4 с 7A); (2) внутри мёртвой зоны. Битый интервал
времени (`dt<=0` или `>1` с — нода подвисла) пропускается, чтобы один разрыв не дал скачок команды.
Отдельного фильтра для D нет намеренно: производная берётся от `distance_m`, уже сглаженной EMA в
детекторе (`distance_ema_alpha`) — шумит D, крутить надо ту EMA, а не заводить второй фильтр.

**Объём урезан против первоначального плана.** Планировался PID на ОБОИХ каналах (+6 параметров),
сделан только на дистанции (+3): там проблема измерена и видна, а доворот по yaw претензий не
вызывал — заводить настройки под несуществующую болезнь незачем (реакция на замечание пользователя
об оверинжиниринге). `kd_yaw` добавим отдельно и по факту, если увидим перелёты доворота.

**Проверено автоматически.** Регресс при `ki=kd=0`: выход **тождественно** равен `0.5·e` на всех
пробах (`+2.00→+1.0000`, `+0.62→+0.3100`, `−0.50→−0.2500`) — поведение M3 не изменилось.
С `ki=0.15` накопитель растёт и добавляет скорость при постоянной ошибке (`+0.3100 → +0.3474` за
5 тиков). Anti-windup: при ошибке 3.0 м интеграл упирается в 2.0 вместо 6.0. Разрыв времени 1.2 с
интеграл не изменил.

**Ловушка, заложенная в конфиг.** `distance_deadband_m: 0.3` — это **пол достижимой ошибки**: дрон
остановится на краю мёртвой зоны, а не на уставке, и I упрётся в неё же. Включая `ki_distance`,
опускать до 0.05–0.1. Записано прямо в `follower.yaml` рядом с параметром.

**Как проверить (гейт 7B).** Запуск как обычно.
1. **Регресс:** дефолтные `ki=kd=0` → поведение неотличимо от 7A (дистанция ~4.6–4.8 м).
2. **Основной эффект:** `ki_distance: 0.15` + `distance_deadband_m: 0.1` → дистанция в оверлее
   подтягивается к **4.0 м**. Это измеримый результат всего инкремента 7.
3. **Граница устойчивости (необязательно, но полезно увидеть):** `ki_distance: 0.6` → дрон
   начинает «дышать» вокруг уставки; `kd_distance: 0.3` эту раскачку гасит.
4. Рабочие значения по итогу зафиксировать в `follower.yaml`.

Параметров в `follower.yaml` стало 30 (было 27): +3 за PID. Чистка 7A (−3) их скомпенсировала.

**Ошибка в 7B, найденная при подборе коэффициентов (2026-07-18).** Первая реализация **сбрасывала
интеграл внутри мёртвой зоны** (`_reset_pid()` при `|e| <= distance_deadband_m`). Логика казалась
разумной («в зоне не копим»), но порождала **автоколебание**: дрон подходит к цели → попадает в
зону → теряет накопленную скорость → встаёт → цель убегает → ошибка снова вырастает → и по кругу.
На модели канала с запаздыванием (детектор 30 Гц + EMA `distance_ema_alpha` + инерция дрона):
размах колебаний **0.34 м**, среднее 4.29 вместо 4.0 — то есть I не давал почти ничего.

Исправлено: мёртвая зона глушит **P и D, но не интеграл**. Внутри зоны дрон едет только на
накопленном — а это ровно постоянная скорость цели, что и требуется. Размах **0.34 → 0.00 м**.
При `ki=0` (дефолт) выход внутри зоны равен нулю, поэтому регресс к M3 сохраняется в точности —
перепроверено: `+2.00→+1.0000`, `+0.62→+0.3100`, `+0.20→0.0000`, `−0.50→−0.2500`.

**Подбор коэффициентов (на модели, не наугад).** Сведение по вариантам:

| ki | kd | мёртвая зона | остаточная ошибка | размах колебаний |
|---|---|---|---|---|
| 0 (было) | 0 | 0.3 | **0.62 м** | 0.00 |
| 0.15 | 0 | 0.1 | **0.10 м** | **0.00** |
| 0.25 | 0 | 0.1 | 0.00 м | 0.21 |
| 0.40 | 0.3 | 0.1 | 0.00 м | 0.22 |

Зафиксировано: **`ki_distance: 0.15`, `kd_distance: 0.0`, `distance_deadband_m: 0.1`**
(0.3 → 0.1, т.к. зона задаёт пол остаточной ошибки). Ошибка удержания падает **0.62 → 0.10 м**
при полном отсутствии колебаний. Вариант `ki=0.25` даёт формально идеальные 4.00 м, но ценой
постоянного «дыхания» ±0.2 м — для демо хуже, чем ровный полёт с ошибкой 0.1 м. `kd` не нужен:
гасить нечего, на модели D не улучшал ни размах, ни среднее.
