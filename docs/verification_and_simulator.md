# Проверка результатов и интеграция с симулятором

Документ описывает способы верификации функционала и механизм интеграции кода с симулятором.
Решения и план — в `project_plan.md` (источник истины).

---

## 1. Верификация и визуализация результатов

Стек предоставляет штатные средства визуализации и количественной оценки.

### Средства визуализации (реального времени)

| Инструмент | Назначение |
|---|---|
| **Gazebo GUI** | 3D-сцена симуляции: положение и движение аппарата относительно цели. |
| **rqt_image_view** | Поток камеры (`/camera/image`); при публикации аннотированного топика — кадр с bbox и смещением цели от центра. |
| **RViz2** | Поза аппарата, траектория, маркеры цели, векторы setpoint'ов. |
| **QGroundControl** | Наземная станция (GCS): положение, режим полёта, телеметрия, arming. |
| **PlotJuggler / rqt_plot** | Временные ряды: ошибка слежения, скорости, setpoint'ы — оценка работы регулятора (P/PID). |

### Критерии корректности контура «детекция → управление»

1. **Демо-видео.** Запись экрана Gazebo + окна аннотированной камеры. Артефакт — в `outputs/videos/`.
2. **Ошибка центрирования.** Смещение цели от центра кадра (px) во времени сходится к нулю по мере
   настройки регулятора — количественный критерий управления. Источник — логи в `outputs/telemetry/`.
3. **Удержание дистанции.** Размер bbox удерживается в заданном коридоре.
4. **Телеметрия** (`outputs/telemetry/`): траектория, скорости, режим, момент входа в offboard.

### Воспроизводимость и офлайн-анализ

- **`ros2 bag record` / `play`** — запись прогона (камера + телеметрия) с последующим
  воспроизведением и анализом без запуска симулятора; пригодно для отладки детектора офлайн.
- Тот же механизм обеспечивает регрессионную проверку: фиксированный bag → детерминированный
  результат перцепции.

### Метрики (черновой набор)

- ошибка центрирования цели (px, среднее / максимум);
- удержание дистанции (отклонение размера bbox от целевого);
- доля кадров с обнаруженной целью (recall слежения);
- частота срывов offboard-режима (целевое значение — 0).

## 2. Интеграция кода с симулятором

### Архитектура связей

```
Gazebo (физика + рендер камеры)
   │  камера → gz-транспорт
   ▼
ros_gz_bridge ──► /camera/image (sensor_msgs/Image)
   ▲
PX4 SITL (автопилот) ◄──► Gazebo (моторы / сенсоры)
   │  uORB-топики через uXRCE-DDS (двунаправленный мост)
   ▼
px4_msgs (ROS2):
   ├─ чтение:  позиция, режим, статус (телеметрия)
   └─ запись:  OffboardControlMode + TrajectorySetpoint + VehicleCommand (управление)
```

Gazebo рассчитывает физику и рендерит камеру. PX4 SITL — процесс автопилота, управляющий
аппаратом в Gazebo. uXRCE-DDS — двунаправленный мост: PX4 публикует uORB-топики в DDS, ROS2
получает их как `px4_msgs`. Узлы `detector_node` и `follower_node` — стандартные ROS2-ноды,
подписанные на эти топики и публикующие в них.

### Компоненты интеграции

1. **PX4-Autopilot** — сборка из исходников. `make px4_sitl gz_x500` поднимает SITL + Gazebo
   с моделью x500 (доступен вариант с камерой); `uxrce_dds_client` стартует автоматически.
2. **Gazebo Harmonic** — зависимость PX4 SITL.
3. **ROS2 Humble** — системная установка (apt).
4. **Micro-XRCE-DDS-Agent** — отдельный процесс: `MicroXRCEAgent udp4 -p 8888`. Без него
   PX4-топики не появляются в `ros2 topic list`.
5. **`px4_msgs`** — клонируется в `src/` workspace (ветка под релиз PX4), собирается через
   `colcon build`; предоставляет ROS2-типы сообщений PX4.
6. **`ros_gz_bridge`** (`ros-humble-ros-gzharmonic`) — проброс камеры Gazebo в ROS2.
7. *(опционально)* **QGroundControl** — GCS для наблюдения и ручного управления.

### Контур управления (offboard)

1. `follower_node` читает `/perception/target` и телеметрию PX4 из `px4_msgs`.
2. Публикует `OffboardControlMode` + `TrajectorySetpoint` непрерывно (>2 Гц).
3. После серии setpoint'ов переключает режим в offboard и выполняет arm (`VehicleCommand`).
4. PX4 исполняет setpoint → Gazebo обновляет состояние аппарата → камера выдаёт новый кадр →
   контур замыкается.

> При падении частоты setpoint'ов ниже 2 Гц PX4 выходит из offboard. Контроллер реализуется
> как непрерывный цикл, а не разовая команда (см. `project_plan.md` §7).

### Распределение по пакетам

| Пакет | Роль |
|---|---|
| `drone_simulator` | launch: PX4 SITL + Micro-XRCE-DDS-Agent + `ros_gz_bridge`. |
| `drone_perception` | `detector_node`: `/camera/image` → `/perception/target`. |
| `drone_control` | `follower_node`: target + телеметрия → setpoints в PX4. |
| `drone_bringup` | сводный launch-файл, объединяющий запуск. |

### Минимальный контур интеграции (критерий go/no-go Фазы 2)

До подключения CV проверяется замкнутость контура ROS2 ↔ PX4 ↔ Gazebo: нода-заглушка
публикует фиксированный setpoint, аппарат взлетает в offboard и удерживает позицию. Успешный
взлёт подтверждает корректность интеграции; параллельно проверяется наличие кадра в
`/camera/image`.
